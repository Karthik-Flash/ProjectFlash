# V1.2.1 Board Results — PYNQ-Z2, 224×224

Every number here comes from a file in the repository. Board numbers come from
`docs/board_runs/`. Derived numbers are recomputed by
`tools/make_report_figures.py` into `docs/figures/derived_numbers.json`.
Labels follow the project brief: **Measured** (tool or board output on the
current design), **Synthesis estimate** (Vivado estimate, including the power
estimate), **Derived** (computed from measured values), **Not yet done**.

## 1. Summary

The V1.2.1 bitstream runs the full 224×224 pneumonia CNN on the PYNQ-Z2
fabric. It is **bit-exact to the NumPy golden model on all 244 verification
images**: logit0, logit1, margin and decision match 244/244 each (Measured,
run 1, 2026-10-09). The same accelerator, rebuilt with an LED GPIO
(`flash_hp64_led`), is bit-exact on the same 244 images (Measured, demo
notebook).

A board-only integration fault caused 0/244 bit-exact on 2026-10-08. It was
located offline with the golden model and fixed in the block design; the RTL
was not changed. On 2026-10-09 the root cause was **confirmed by
intervention on the board**. With the same 32-bit bitstream on the same boot,
setting one PS register bit took the result from 0/244 to 244/244 (runs 2
and 3).

Compute latency is 182.94 ms per image (12,196,126 cycles at 66.67 MHz). End
to end, with host overhead, it is 184.73 ms (Measured). The board's ARM core
runs the same golden model 3.6–4.1× slower than the FPGA computes (Derived).
At T = −646, the board's decisions on the 244 images give sensitivity 0.959
and specificity 0.467 (Measured, n = 244). The headline model metric stays
the test-set AUROC of 0.8229 over 4,003 patients.

## 4. Root cause of the 2026-10-08 failure

Full analysis: [`V1_board_debug_log.md`](V1_board_debug_log.md).

- **Symptom.** 0/244 bit-exact, yet board and expected logits correlate at
  r = 0.98 and 234/244 decisions agree (Derived). The fault was
  deterministic, unchanged at 25, 50 and 66.67 MHz, and carried no state
  between runs. The DMA reported no errors.
- **Model.** `board == golden(dup_even(x))`: every odd 32-bit input word is
  replaced by the even word before it. This matches 244/244 images and 24/24
  probes (Derived). It predicted the two probes that separate it from the
  golden model before they were run: px(1,0) → (−349, 102, 451) and
  px(223,223) → the const-0 result. Both came out as predicted.
- **Mechanism.** The design had a 32-bit HP0 port, but the HP0 AFI was in
  64-bit mode (RDCHAN_CTRL bit 0 = 0). PYNQ does not run the design's
  `ps7_init`, which is where the AFI width would be set. Each 32-bit read
  therefore returned the low half of a 64-bit word.
- **Confirmation (2026-10-09).** Same 32-bit bitstream, same boot: flipping
  that one PS register bit took the result from 0/244 to 244/244 (runs 2 and
  3).
- **Fix (V1.2.1).** HP0 and the DMA memory side are 64-bit, which matches
  PYNQ's default AFI mode, so no runtime register write is needed. Result:
  244/244 (run 1). Vivado refuses a direct DMA→HP0 connection (AXI4 vs AXI3),
  so an `auto_pc` protocol converter sits between them. The accelerator
  netlist is unchanged: its 2,274 `INIT_xx` lines (weight, bias and layer
  ROM contents) are identical to the V1.2 build.
- **Why simulation missed it.** `tb_v1_axi` drives the AXI-Stream input
  directly; the PS, AFI and DDR are not modelled. The board notebooks now
  check the AFI against the `.hwh` on every load. For V2, either model the
  memory path in simulation or keep that check.
- **Why the corrupted result looked plausible.** Repeating 4-pixel groups
  acts like a slight horizontal blur, and the global-average-pooling CNN is
  robust to it. Decision-level agreement (234/244) would have hidden the bug.
  **Only logit-level bit-exact comparison caught it.**

The CYCLES count is 3,230 more than the 12,192,896 MACs of the network.
3,136 of those are the GAP stream (64 channels × 7 × 7, one value per cycle)
and 94 are sequencing and pipeline drain (Derived). The accelerator does
**one MAC per cycle by design**.

## 6. ARM Cortex-A9 baseline

Same golden model (NumPy int64) on the board's PS, image 0, one timed run per
session:

| Run | ARM ms (image 0) | Model load |
|---|---|---|
| 1 | 743.9 | 0.20 s |
| 2 | 726.3 | 0.19 s |
| 3 | 665.1 | 0.19 s |
| demo (12 images) | mean 706.6 (699.1–731.1) | — |

- Every ARM result equals `exp_*[0]` (12/12 in the demo), so the ARM and the
  FPGA produce **the same integers**.
- FPGA compute is **3.6–4.1× faster** than the ARM: 665.1–743.9 ms against
  182.94 ms (Derived). In the demo, the mean speedup over `run()` was 3.8×
  (Measured).
- This baseline is limited. It is unoptimised NumPy int64 on one core,
  timed on one image per session. A NEON int8 implementation would be
  faster.
- Context: the same golden model takes **8.7 ms/image** on the development
  PC (13th Gen Intel Core i7-13650HX, NumPy 2.3.5, median of 21 runs;
  `docs/figures/pc_golden_timing.json`, `tools/time_golden_pc.py`). The V1
  engine does one MAC per cycle by design, so a desktop CPU is faster. V1
  proves a bit-exact integer pipeline. Parallel MACs are V2 work; 14 of 220
  DSPs are used.

## 7. Classification on the 244 verification images

These are board-measured values, identical to the golden model by
construction. The 244 are held-out test images: a seeded, balanced subset
(122 positive, 122 negative) of the 4,003-patient test split.

Confusion matrix at T = −646. The rule is `margin > T`; no margin equals T,
so `>=` gives the same result.

| | Predicted pneumonia | Predicted no pneumonia |
|---|---|---|
| **Pneumonia (122)** | TP 117 | FN 5 |
| **No pneumonia (122)** | FP 65 | TN 57 |

- Sensitivity **0.959** (Wilson 95% CI 0.908–0.982).
- Specificity **0.467** (0.381–0.555).
- PPV 0.643, NPV 0.919, accuracy 0.713 (174/244).
- **AUROC from the board margins: 0.837** (bootstrap 95% CI 0.785–0.884;
  2,000 resamples of the 244, seed 0, percentile). This is consistent with
  the full-test-set AUROC of 0.8229 (95% CI 0.8083–0.8379, 4,003 patients,
  `v1/mem/v1_2/flash_v1_2/manifest.json`). **The headline accuracy metric
  stays 0.8229 with its CI.**
- **The errors are mostly false positives: 65 FP against 5 FN.** That is
  the chosen operating point, not a hardware effect. T = −646 was picked on
  *validation* data to reach ≥ 90% sensitivity, a screening point.
- **The false negatives are near-misses.** Their margins are −736, −719,
  −712, −712 and −670, all within 90 of T.
- **The false positives are spread out.** Their margins run from −639 to
  +1,928, with quartiles −318 / 0 / +593. The median margin is +792.5 for
  positives and −595.5 for negatives, so 65 of the 122 negative images lie
  above T.
- **Overfitting.** This data shows no sign of it: the 244 are held-out test
  images, and their AUROC matches the test-set figure. The Colab notebook in
  the repository has no saved training curves, so no train-versus-validation
  claim is made either way.
- **Threshold trade-off, illustrative only.** This table is computed on test
  images, so it must **not** be used to choose a threshold. A new threshold
  has to come from validation data.

| T | Sensitivity | Specificity |
|---|---|---|
| −646 | 0.959 | 0.467 |
| −400 | 0.885 | 0.566 |
| −200 | 0.852 | 0.656 |
| 0 | 0.779 | 0.738 |
| +200 | 0.713 | 0.787 |

- **The RSNA "Not Normal" label, checked on the 244.** In RSNA, label 0
  combines "Normal" and "No Lung Opacity / Not Normal". The manifest records
  this three-way class (from RSNA's `stage_2_detailed_class_info.csv`) for
  every verification image. Of the 76 "Not Normal" negatives, **50 (65.8%)**
  are false positives. Of the 46 "Normal" negatives, **15 (32.6%)** are
  (Derived). On the full test set the same split shows: AUROC 0.9363 for
  pneumonia vs Normal, against 0.7382 for pneumonia vs Not Normal
  (manifest). Most false positives are therefore abnormal-but-not-pneumonia
  studies. That is a property of the label definition, and the V2 first task
  below.

## 8. Power

The only figures are Vivado's vector-less estimates (Synthesis estimate):
1.494 W total for V1.2.1 (confidence Medium) and 1.499 W for V1.2.1-led
(confidence Low). The PS7 accounts for 1.256 W of either; the programmable
logic's dynamic power is under 0.1 W. These are estimates, not board
measurements. A measurement with an inline USB power meter (idle and while
running), or a SAIF-based estimate from post-implementation simulation, is
future work (Not yet done).

## 9. Limitations

- 66.67 MHz rather than 75 MHz. The conv_engine address path is the
  critical path. At 71.43 MHz, the next PS clock step, it failed post-route
  timing by 0.925 ns. Pipelining that address path is a V2 item.
- One MAC per cycle, hence 183 ms per image.
- The sensitivity and specificity above come from 244 images. An AUROC of
  0.82 is research grade, not clinical.
- The DICOM → board path has not been run end to end on the board.
- Not a medical device.

## 10. Reproduce

`v1/board/README.md` gives the lab order: fresh boot → `flash_hp64` →
`flash_hp32` (AFI_FORCE off, then on) → reboot. Build the bundle with
`v1/board/make_board_bundle.ps1` (263 files, including both demo overlays
and the demo notebook). The notebooks are generated by
`v1/board/make_notebook.py` and `v1/board/make_demo_notebook.py`.
